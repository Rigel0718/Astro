지금까지 Python의 객체가 무엇인지부터 시작해서 객체가 메모리에 어떻게 존재하고, 이름과 어떻게 연결되며, attribute를 어떻게 저장하고 탐색하는지 살펴보았다.

그렇다면 마지막으로 이런 질문을 해볼 수 있다.

> **한 번 만들어진 객체는 언제 메모리에서 사라질까?**

```python
a = [1, 2, 3]
```

이 코드가 실행되면 `[1, 2, 3]`이라는 객체가 만들어지고 `a`라는 이름이 그 객체를 참조한다.

그런데 다음과 같이 작성하면 어떻게 될까?

```python
del a
```

흔히 `del`을 보고 **"객체를 삭제한다"** 고 생각하기 쉽다.

하지만 정확히는 그렇지 않다.

`del a`가 직접 객체를 삭제하는 것이 아니라, **이름 `a`와 객체 사이의 연결을 제거한다.**

그렇다면 연결이 끊어진 객체는 어떻게 되는 걸까?

이 질문에 답하려면 Python 객체의 마지막 단계인 **객체의 생명주기(object lifecycle)** 를 이해해야 한다.

---

## 1. 객체는 참조되고 있는 동안 살아있다

먼저 다음 코드를 보자.

```python
a = [1, 2, 3]
b = a
```

현재 관계를 단순화하면 다음과 같다.

```text
a ───┐
     │
     ├────→ [1, 2, 3]
     │
b ───┘
```

`a`와 `b`는 서로 다른 객체를 가지고 있는 것이 아니다.

두 이름이 **동일한 객체를 참조하고 있다.**

여기서 다음 코드를 실행한다.

```python
del a
```

그러면 관계는 다음과 같이 변한다.

```text
b ─────────→ [1, 2, 3]
```

`a`라는 이름과 객체 사이의 연결만 사라졌다.

객체 자체는 여전히 `b`가 참조하고 있으므로 살아있다.

즉,

```python
del a
```

는

> **"a가 가리키는 객체를 삭제해라"**

가 아니라

> **"현재 namespace에서 a라는 이름의 binding을 제거해라"**

에 가깝다.

이 차이가 중요하다.

Python에서 이름과 객체는 서로 독립적이기 때문이다.

---

## 2. 그렇다면 객체는 언제 정말 사라질까?

Python 언어 수준에서는 객체가 더 이상 도달 가능하지 않을 때 객체의 수명이 끝날 수 있다.

그리고 우리가 지금까지 살펴본 **CPython**에서는 이를 관리하는 핵심 메커니즘 중 하나로 **reference counting**을 사용한다.

CPython 객체의 기본 구조를 다룰 때 다음과 같은 구조를 살펴보았다.

```c
typedef struct _object {
    Py_ssize_t ob_refcnt;
    PyTypeObject *ob_type;
} PyObject;
```

여기서 다시 등장하는 것이

```text
ob_refcnt
```

이다.

`ob_refcnt`는 해당 객체가 현재 얼마나 참조되고 있는지를 관리하기 위한 값이다.

개념적으로 생각하면 다음과 같다.

```python
a = []
```

```text
a ─────→ []
          refcount 증가
```

그리고

```python
b = a
```

가 실행되면 또 하나의 참조가 생긴다.

```text
a ───┐
     ├────→ []
b ───┘
```

반대로 참조가 제거되면 reference count도 감소할 수 있다.

```python
del a
```

```text
b ─────────→ []
```

마지막 참조까지 사라져 reference count가 0이 되면 CPython은 해당 객체를 정리할 수 있다.

```python
del b
```

```text
[]
refcount = 0

↓
객체 정리
```

그래서 CPython에서는 많은 객체가 **마지막 참조가 사라지는 시점에 즉시 정리되는 것처럼 보인다.**

---

## 3. `del`은 객체 삭제 명령이 아니다

이제 `del`의 의미를 조금 더 정확하게 볼 수 있다.

```python
a = [1, 2, 3]
b = a

del a
```

여기서 `del a`가 `[1, 2, 3]` 객체를 직접 파괴했다면 `b`도 사용할 수 없어야 한다.

하지만 실제로는 그렇지 않다.

```python
print(b)
# [1, 2, 3]
```

객체는 그대로 살아있다.

사라진 것은 `a`라는 이름이다.

따라서 다음 두 개념을 분리해서 생각해야 한다.

```text
del a
    ↓
이름과 객체의 binding 제거

마지막 reference 제거
    ↓
객체가 더 이상 필요하지 않게 됨
    ↓
객체의 수명 종료
```

이것은 우리가 앞에서 살펴본

> **Python의 변수는 값을 담는 상자가 아니라 이름과 객체의 binding이다.**

라는 개념의 자연스러운 결과다.

객체의 생성과 소멸 역시 결국 **이름이 아니라 객체와 reference를 중심으로 이해해야 한다.**

---

## 4. `__del__`은 무엇일까?

Python에는 객체가 정리되는 과정에 관여할 수 있는 특별한 메서드도 존재한다.

```python
class Person:
    def __del__(self):
        print("Person 객체 정리")


p = Person()
del p
```

CPython에서 다른 참조가 없다는 단순한 상황이라면 다음과 같은 결과를 볼 수 있다.

```text
Person 객체 정리
```

`__del__`은 객체가 finalization되는 과정에서 호출될 수 있는 **finalizer**다.

다만 여기서 주의해야 한다.

```python
del p
```

가 곧바로

```python
p.__del__()
```

을 의미하는 것은 아니다.

`del p`는 여전히 **이름 `p`의 binding을 제거하는 연산**이다.

단순한 CPython 상황에서는 이것이 마지막 참조를 제거하고, 그 결과 객체의 finalization이 진행되면서 `__del__`이 호출될 수 있는 것이다.

즉 관계는 개념적으로 다음에 가깝다.

```text
del p
  ↓
p라는 binding 제거
  ↓
마지막 reference가 사라짐
  ↓
객체 finalization
  ↓
__del__ 호출 가능
  ↓
객체 정리
```

또한 `__del__`은 프로그램 종료 시점, 순환 참조, 객체가 다시 살아나는 resurrection 같은 문제까지 고려하면 동작을 단순하게 예측하기 어렵다.

그래서 파일이나 네트워크 연결 같은 중요한 자원의 해제를 `__del__`에만 맡기는 방식은 일반적으로 권장되지 않는다.

이런 자원은 보통 context manager를 이용한다.

```python
with open("data.txt") as f:
    data = f.read()
```

여기서 중요한 것은 **객체의 메모리 수명과 외부 자원의 수명을 반드시 같은 것으로 생각해서는 안 된다는 것**이다.

---

## 5. Reference Count만으로 충분하지 않은 이유

그런데 reference counting에는 한 가지 중요한 문제가 있다.

바로 **순환 참조(cyclic reference)** 다.

다음과 같은 구조를 생각해보자.

```python
class Node:
    pass


a = Node()
b = Node()

a.other = b
b.other = a
```

현재 객체의 관계는 다음과 같다.

```text
a ─────→ Node A
          │   ↑
          ↓   │
         Node B
            ↑
            │
b ──────────┘
```

`Node A`는 `Node B`를 참조하고,

`Node B`는 다시 `Node A`를 참조한다.

이제 외부의 이름을 제거해보자.

```python
del a
del b
```

그러면 프로그램에서는 더 이상 두 객체에 접근할 방법이 없다.

```text
        Node A
         ↓  ↑
         ↑  ↓
        Node B
```

외부에서는 이 객체들에 도달할 수 없다.

사실상 더 이상 필요 없는 객체다.

그런데 문제가 있다.

```text
Node A → Node B
Node B → Node A
```

서로가 서로를 참조하고 있기 때문에 단순한 reference counting만 보면 각 객체의 reference count가 0이 되지 않을 수 있다.

이것이 **순환 참조 문제**다.

---

## 6. 그래서 Garbage Collector가 필요하다

CPython은 이런 문제를 해결하기 위해 reference counting과 함께 **cyclic garbage collector**를 사용한다.

중요한 점은 둘의 역할이 조금 다르다는 것이다.

```text
Reference Counting
        ↓
일반적인 객체 수명 관리

Cyclic Garbage Collector
        ↓
reference counting만으로 정리하기 어려운
순환 참조 탐지 및 수거
```

즉 CPython의 메모리 관리를 단순히

> "Garbage Collector가 필요 없는 객체를 찾아서 지운다."

라고만 설명하면 실제 구조를 놓치게 된다.

CPython에서는 reference counting이 객체 수명 관리의 중심적인 역할을 하고, cyclic GC가 **순환 참조라는 약점을 보완한다.**

예를 들어 앞의 두 객체는 서로를 참조하고 있지만 프로그램의 살아있는 객체들로부터 더 이상 도달할 수 없다.

```text
Program

   X
   │ 접근 불가능
   │
   ┌─────────┐
   │ Node A  │
   │    ↓    │
   │ Node B  │
   │    ↑    │
   └─────────┘
```

GC는 이런 **도달 불가능한 순환 객체 집합**을 찾아 정리할 수 있다.

---

## 7. GC는 모든 객체를 계속 검사할까?

그렇다면 Garbage Collector가 프로그램에 존재하는 모든 객체를 매 순간 검사해야 할까?

그렇게 한다면 비용이 너무 클 것이다.

CPython의 cyclic GC는 추적 대상 객체들을 **세대(generation)** 개념으로 관리하며, 오래 살아남은 객체일수록 상대적으로 덜 자주 검사하는 전략을 사용한다.

핵심 아이디어는 단순하다.

> **대부분의 객체는 짧게 살고, 오래 살아남은 객체는 앞으로도 살아남을 가능성이 높다.**

예를 들어 함수 안에서 잠시 사용하는 리스트를 생각해보자.

```python
def calculate():
    values = [1, 2, 3]
    return sum(values)
```

`values`가 참조하는 리스트는 함수 실행 중 잠시 사용되고 곧 필요 없어질 가능성이 높다.

반면 프로그램이 시작될 때 생성되어 계속 유지되는 객체라면 앞으로도 오래 살아있을 가능성이 상대적으로 높다.

GC는 이러한 특성을 이용해 모든 객체를 똑같은 빈도로 검사하지 않는다.

다만 CPython의 GC 구현 세부사항과 generation 구성은 Python 버전에 따라 달라질 수 있다.

따라서 여기서는 구체적인 세대 개수나 내부 알고리즘 자체보다,

> **CPython은 reference counting을 기본으로 사용하고, 추적 가능한 객체의 순환 참조를 별도의 GC가 보완한다.**

정도로 이해하는 것이 핵심이다.

## 8. 객체의 전체 생명주기

이제 지금까지 배운 내용을 하나의 흐름으로 연결해보자.

```python
a = Person()
```

객체가 생성된다.

```text
Person()
   ↓
메모리에 객체 생성
   ↓
a가 객체를 참조
```

다른 이름이 같은 객체를 참조할 수도 있다.

```python
b = a
```

```text
a ───┐
     ├────→ Person object
b ───┘
```

객체는 프로그램에서 사용된다.

```python
a.name
a.run()
```

이 과정에서 앞선 글에서 살펴본 attribute lookup, descriptor, class, inheritance, MRO 같은 메커니즘이 동작한다.

그리고 참조가 하나씩 사라진다.

```python
del a
del b
```

일반적인 경우 CPython에서는 마지막 참조가 사라지면서 객체가 정리된다.

하지만 순환 참조가 존재한다면 cyclic GC의 도움이 필요할 수도 있다.

결국 전체 흐름을 단순화하면 다음과 같다.

```text
객체 생성
   ↓
메모리에 객체 존재
   ↓
이름 / 컨테이너 / 다른 객체 등이 reference
   ↓
객체 사용
   ↓
reference 제거
   ↓
더 이상 객체에 도달할 수 없음
   ↓
┌─────────────────────────────┐
│ 일반적인 경우               │
│ reference counting으로 정리 │
│                             │
│ 순환 참조가 있는 경우       │
│ cyclic GC가 보완            │
└─────────────────────────────┘
   ↓
객체의 생명주기 종료
```

## 9. Python 객체를 바라보는 하나의 흐름

이 시리즈의 처음으로 돌아가보자.

우리는 처음에 이런 질문에서 시작했다.

> **Python에서 객체란 무엇일까?**

Python에서 우리가 다루는 값은 객체로 표현되고, 이름은 그 객체에 binding된다.

```python
a = 10
```

이것은 단순히 변수라는 상자에 `10`을 집어넣는 것으로만 이해하기보다,

```text
a ─────→ 10 object
```

라는 관계로 이해하는 편이 Python의 객체 모델에 더 가깝다.

CPython으로 한 단계 내려가면 객체는 `PyObject`를 기반으로 한 메모리 구조로 표현되고, 객체는 자신의 타입에 대한 정보를 가지고 있다.

클래스 역시 객체이며, 객체의 attribute는 instance와 class의 namespace 등에 저장된다.

```text
obj
 ↓
attribute lookup
 ↓
instance / descriptor / class
 ↓
inheritance
 ↓
MRO
```

그리고 객체가 사용되는 동안 수많은 reference가 생기고 사라진다.

마지막에는 더 이상 필요하지 않은 객체가 정리된다.

결국 지금까지 살펴본 내용을 하나의 흐름으로 표현하면 다음과 같다.

```text
객체란 무엇인가
      ↓
이름은 객체와 어떻게 연결되는가
      ↓
CPython에서 객체는 메모리에 어떻게 존재하는가
      ↓
Class는 어떻게 객체가 되는가
      ↓
Attribute는 어디에 저장되는가
      ↓
Attribute는 어떻게 읽히는가
      ↓
상속하면 Attribute를 어디서 찾는가
      ↓
객체는 언제 메모리에서 사라지는가
```

처음부터 끝까지 중심에 있었던 것은 결국 하나다.

**객체와 객체 사이의 관계다.**

이름은 객체를 참조하고,

객체는 자신의 type과 연결되어 있으며,

instance는 class와 연결되어 있고,

class는 base class와 연결되어 있으며,

attribute 탐색은 이러한 관계를 따라 이루어진다.

그리고 마지막 reference가 사라지면 객체의 생명주기도 끝을 향한다.

## 마무리

Python을 처음 배울 때는 보통 문법을 중심으로 배운다.

```python
a = 10

class Person:
    pass

p = Person()
p.name = "Kim"

del p
```

하지만 객체 모델을 이해하고 나면 같은 코드가 조금 다르게 보이기 시작한다.

```text
이름
 ↓
reference
 ↓
object
 ↓
type
 ↓
class
 ↓
namespace
 ↓
attribute lookup
 ↓
inheritance / MRO
 ↓
reference 제거
 ↓
object lifecycle 종료
```

Python의 문법 뒤에서는 객체들이 만들어지고, 서로 연결되고, 탐색되고, 다시 연결이 끊어진다.

그래서 Python에서

> **Everything is an object.**

라는 말은 단순히 "Python에는 객체가 많다"는 의미가 아니다.

Python이라는 언어의 수많은 기능이 **공통된 객체 모델 위에서 연결되어 동작한다**는 의미에 더 가깝다.

변수도, 함수도, 클래스도 서로 완전히 별개의 세계에 존재하는 것이 아니라 객체라는 공통된 모델 안에서 다뤄진다.

그리고 그 객체들은 생성되고, 참조되고, 사용되고, 마지막에는 사라진다.

그 전체 흐름을 이해하는 것이 Python의 객체 모델을 이해하는 일이다.
